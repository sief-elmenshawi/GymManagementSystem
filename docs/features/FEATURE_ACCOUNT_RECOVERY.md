# Feature: Email confirmation and password recovery

Status: **Done**

## Purpose

Require ownership of an email address before sign-in, and let any account holder reset a forgotten password without exposing whether an email is registered.

## Actors and authorization

| Actor | Access |
| --- | --- |
| Anonymous visitor | `/Account/ConfirmEmail`, `/Account/ResendEmailConfirmation`, `/Account/ForgotPassword`, `/Account/ResetPassword` |
| `Member` | Same anonymous recovery flow after confirmation |
| `Admin` / `SuperAdmin` | Same anonymous recovery flow; seeded accounts are already confirmed |
| Developer only | `/dev-mailbox/{email}` and `DELETE /dev-mailbox` |

All account actions allow anonymous access. The development mailbox endpoints are mapped only when `IWebHostEnvironment.IsDevelopment()` is true.

## Scope

* `IdentityOptions.SignIn.RequireConfirmedAccount = true` and `RequireConfirmedEmail = true`
* `.AddDefaultTokenProviders()` so Identity can issue confirmation/reset tokens
* Confirmation email on public registration
* `/Account/ConfirmEmail?userId=...&token=...`
* `/Account/ResendEmailConfirmation` GET/POST and generic confirmation page
* `/Account/ForgotPassword` GET/POST and generic confirmation page
* `/Account/ResetPassword?email=...&token=...` GET/POST
* Login link to **Forgot password?** and a clear blocked-login message before confirmation
* Seeded and SuperAdmin-created accounts are auto-confirmed
* Optional SMTP sender; in-memory mailbox fallback for Development

## Business rules

* Tokens are generated by ASP.NET Core Identity and are single-use/expiring.
* Registration always creates the `Member` role and a linked `Member` record; no role input is accepted.
* Registration succeeds even if an email cannot be delivered; failures are logged instead of deleting the account.
* Resend confirmation always shows the same confirmation message and sends a fresh link only when the account exists and is still unconfirmed.
* Forgot password always shows the same confirmation message and sends nothing for unknown emails.
* Password reset does not bypass email confirmation; an unconfirmed account still needs confirmation to sign in.
* SMTP is used only when `Email:Smtp:Host` is configured. Credentials come from configuration/environment, never source control.
* In Development with no SMTP host, messages are stored in memory and exposed through `/dev-mailbox/{email}`.

## Configuration

| Key / environment variable | Purpose |
| --- | --- |
| `Email:From` / `Email__From` | Sender address |
| `Email:Smtp:Host` / `Email__Smtp__Host` | SMTP host |
| `Email:Smtp:Port` / `Email__Smtp__Port` | SMTP port, default `587` |
| `Email:Smtp:UseSsl` / `Email__Smtp__UseSsl` | SSL/STARTTLS, default `true` |
| `Email:Smtp:User` / `Email__Smtp__User` | SMTP username |
| `Email:Smtp:Password` / `Email__Smtp__Password` | SMTP secret |

## User flows

1. Visitor registers; the account is created unconfirmed and a confirmation email is sent.
2. Login with an unconfirmed account returns a validation message instead of a session.
3. Visitor opens the emailed link; `ConfirmEmail` validates the token and redirects to login.
4. If the link is lost, the visitor selects **Resend confirmation?** and receives the same generic confirmation page; only an existing unconfirmed account gets a new link.
5. Visitor opens **Forgot password?**, submits an email, and receives a generic confirmation page.
6. If the account exists, a reset link is emailed; the visitor posts a new password with the hidden token.
7. The old password no longer works and the new password signs in normally.

## Risks and follow-ups

* **Resolved:** resend-confirmation GET/POST exists and reissues a link only for an existing unconfirmed account, with the same generic response for confirmed and unknown emails.
* **Accepted by design:** SMTP delivery failures are logged but do not roll back registration or change the confirmation state. They now also increment the `GymManagement.Email` / `email_delivery_failures` counter (tagged by reason and SMTP host); see [Production configuration](../deployment/PRODUCTION_CONFIGURATION.md#email-delivery-monitoring) for alert guidance.
* **Accepted by design:** the development mailbox is in-memory, cleared on restart, and mapped only in Development. Production uses configured SMTP and has no mailbox endpoint.
